# Публикация репозитория: чистка почты из истории

> Вне OWNS: `docs/runbooks/**` принадлежит ops — разовое исключение по решению владельца 2026-10-21. Скрипты **ничего не пушат сами**; шаги 3–4 выполнять только по команде владельца.

Цель: убрать старые личные адреса (передаются скрипту через `OLD_EMAILS`, в репозитории не хранятся) из автора/коммиттера всех коммитов (замена: `geone39 <50493709+geone39@users.noreply.github.com>`). Проверено на копии: 81 коммит до и после, деревья всех веток идентичны, остаётся только noreply (и `GitHub <noreply@github.com>` как коммиттер веб-мержей).

## Побочные эффекты
- **Все хэши меняются.** Открытые PR-ветки и worktree других сессий разойдутся с новым `main`. Перенос: `rebase-branch.sh commit-map.txt <ветка>` (`git rebase --onto <новый_хэш_базы> <старый_хэш_базы>`), затем `push --force-with-lease`. Карта «старый→новый» — `commit-map.txt` от `rewrite-history.sh`.
- **Переписывание «на месте» не чистит полностью.** GitHub хранит старые коммиты по хэшу и в `refs/pull/*/head` (PR #8…#139), а `.patch`/`.diff` страниц PR показывают почту автора. Для настоящей очистки нужен запрос в GitHub Support («Sensitive data removal», после force-push; удалить кэш и `refs/pull`) — результат не мгновенный и не гарантирован по срокам.
- **Новый репозиторий** этого избегает: нет `refs/pull`, старых объектов. Цена: теряются PR, Issues, комментарии, звёзды/ссылки; нужно перепривязать remote у всех сессий.

## Сравнение
| | 1. На месте | 2. Новый репозиторий |
|---|---|---|
| Почта в публичном доступе | остаётся в старых объектах/PR, пока Support не очистит | нет |
| История PR/Issues | сохраняется (PR-ветки надо перенести) | теряется (Issues переносятся скриптом, без комментариев) |
| Сложность | средняя + ожидание Support | выше разово, проще потом |
| Риск | force-push ломает чужие ветки | теряются обсуждения PR |
| Ссылки/настройки (Secrets, Actions, Pages) | сохраняются | настраивать заново |

**Рекомендация: сценарий 2** (новый публичный репозиторий; старый — удалить или оставить приватным архивом). Только он гарантирует отсутствие почты в публичных объектах. Сценарий 1 — если важнее сохранить PR/Issues и допустимо ждать Support.

## Подготовка (один раз, делает владелец)
1. GitHub → Settings → Emails: включить **Keep my email addresses private** и **Block command line pushes that expose my email**.
2. У агентов: `git config user.email 50493709+geone39@users.noreply.github.com` (в репозитории локально уже стоит).
3. Влить PR `chore/publish-prep` (лицензия, нейтрализация, README) **до** переписывания — иначе его придётся переносить.
4. Заморозить работу: все сессии закончили/запушили свои ветки.

## Шаги
```bash
# 0. Переписать в scratch-папке (коротким путём на Windows, иначе "Filename too long"). Ничего не пушит.
pip install git-filter-repo
OLD_EMAILS="<адрес1> <адрес2>" bash docs/runbooks/publish/rewrite-history.sh /c/Users/<вы>/fl-rewrite
```
Скрипт сам проверяет: нет старых адресов, деревья веток идентичны, число коммитов то же.

**Сценарий 1 (на месте):**
```bash
bash docs/runbooks/publish/push-in-place.sh /c/Users/<вы>/fl-rewrite   # --force-with-lease по каждой ветке
```
Затем: каждая сессия `git fetch` + `rebase-branch.sh`; запрос в GitHub Support на очистку кэша и `refs/pull`; потом Settings → General → Change visibility → Public.

**Сценарий 2 (новый репозиторий):**
```bash
bash docs/runbooks/publish/push-new-repo.sh /c/Users/<вы>/fl-rewrite fireline-public   # gh repo create --public + push main
bash docs/runbooks/publish/migrate-issues.sh geone39/fireline geone39/fireline-public
```
Затем в каждой сессии: `git remote set-url origin https://github.com/geone39/fireline-public.git`, ветки переносить через `rebase-branch.sh` (база — из `commit-map.txt`) и пушить как новые PR. Включить защиту `main`, Actions; старый репозиторий — удалить/архивировать после проверки. Обновить ссылки в README/доках, если есть абсолютные URL.

## Что может сломаться
- Незапушенные/неперенесённые ветки с новой работой (сначала дождаться merge или перенести).
- Открытые PR в старом репозитории (сценарий 2: закрыть, пересоздать).
- Клоны других сессий: `git pull` даст расхождение — не мерджить, а `fetch` + `reset --hard origin/main` (если нет локальной работы) или `rebase --onto`.
- Подписи коммитов (если были) исчезнут — у переписанных коммитов подписи недействительны.
