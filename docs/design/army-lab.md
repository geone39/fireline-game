Статус: черновик под ARMY-1 (обучение, лагеря, housing) и ARMY-2 (лаборатория). Основание: решение владельца 2026-10-19 (OQ-QA2-LEVELS, Issue #86): **уровень юнитов атакующего определяется лабораторией** (`content/research.yaml`), вместимость лагерей, гаражей и Центра поддержки задаётся там же (в контенте — по уровням зданий). **Все числа баланса в спеке — ключи контента.** Числа в примерах (§9) — тестовая фикстура, не баланс. Значения «ориентир» взяты из `tools/simbattle/assumptions.yaml` и существующих yaml только как отправная точка: окончательные решает владелец/balance.

## 1. Модель данных (что хранит игрок)

| Сущность | Что это | Где живёт |
|---|---|---|
| `stock[unit_id] = count` | обученные юниты «дома» (техника, корабли — тоже). Уровня у экземпляра **нет** | сервер, таблица армии |
| `spells[spell_id] = count` | готовые заклинания (Support calls) | сервер |
| `deployed[raid_id][id] = count` | юниты/заклинания, «отданные» в активный рейд (escrow, §6) | сервер |
| `queue[building_id] = [order]` | очередь обучения здания; `order = {order_id, unit_id, count, remaining}` | сервер |
| `research_done = {node_id}` и `research_active = {node_id, started_at, finish_at, paid}` | состояние лаборатории (одно активное) | сервер |
| `perks` | производная от `research_done` (§5.5) | вычисляется |

Принцип: **уровень — свойство типа юнита у игрока**, а не экземпляра. Армия — это счётчики. Поэтому «армия не портится» и «новый уровень получают все» (§2.2) — следствия модели, а не отдельные механики.
ASSUMPTION (запрос SERVER-4): таблица `army` из `docs/04-data-model.md` (`PRIMARY KEY(player_id,unit_id,level)`) хранит `(player_id, unit_id, count)`; колонка `level` не нужна (если остаётся — всегда `0` и не читается). Иначе пришлось бы «перебрасывать» счётчики при каждом исследовании.

Все времена — секунды сервера (`server_time`), целые числа. Состояние очередей и исследования **ленивое**: пересчитывается при каждом чтении (`GET /v1/army`, `GET /v1/lab`) и при любой мутации, как таймеры базы (`api` §«Базa»). Фоновых воркеров для корректности не нужно; SSE `training_done` / `research_done` — только уведомление.

## 2. Уровень юнита = лаборатория

### 2.1 Правило

```
Level(item) = max(1, max{ node.to_level | node ∈ research_done, node.unit == item  или  node.spell == item })
```
- `item` — юнит (`u_*`, `v_*`, `s_*`) или заклинание (`c_*`). Узлов нет → уровень 1 навсегда.
- Уровень применяется ко **всему** запасу данного типа сразу; боевые статы — по `battle-sim.md` §3.2 (`hp·Mhp[L]`, `dmg·Mdps[L]`, рост — `level_growth` в `troops.yaml`).
- `to_level` узла — абсолютный уровень, а не «+1»: `r_rifle_2` (`to_level: 4`) даёт 4 сразу (3-й уровень «перескакивается»; формулы работают для любого целого `L ≥ 1`).
- Цепочка узлов одного предмета — по возрастанию `to_level`. ASSUMPTION: узел доступен, только если выполнены все узлы того же предмета с меньшим `to_level` (явный `requires` — CONTENT-REQ, §11, на будущее).
- Герои: их уровень — отдельная система (`heroes.md`, `b_command`, alloy+fuel), в `Army.Hero.Level` берётся оттуда; лаборатория на героев не влияет.

### 2.2 Когда исследование «срабатывает» (ответ на «уже обученные тоже?»)
**Да, все.** Момент `research.finish_at` — событие «узел выполнен»: `research_done += node`. С этого момента:
1. любые **новые** формирования `Army` (§6) используют новый уровень — для обученных ранее и для обучаемых сейчас;
2. очередь обучения **не** перезапускается и не пересчитывается (стоимость и время юнита от уровня не зависят — ASSUMPTION, иначе исследование «ломало» бы уже оплаченные заказы);
3. **бой, уже начатый** (выдан `RaidTicket`), уровни не меняет: `Level` каждого слота зафиксирован в тикете (§6.2). Исследование, завершившееся во время боя, действует в следующем бою;
4. UI: в списке армии у типа появляется бейдж нового уровня; в «Итоге боя»/«Экране выбора» уровень показан всегда.

### 2.3 Юниты без узлов
В `research.yaml` сейчас 12 узлов (8 юнитов/техники, 1 заклинание, 3 перка). Остальные юниты, техника, корабли и заклинания остаются 1-го уровня, пока `content` не добавит узлы (CONTENT-REQ §11 п.5; решает balance). Это допустимое состояние для релиза; симулятор `simbattle` (`-levels research`) считает именно так.

## 3. Housing (вместимость армии)

### 3.1 Три пула
| Пул | Что занимает | Здания | Единица |
|---|---|---|---|
| `unit` | пехота и дроны: классы `INF`, `AIR` (`troops:`) | `b_camp` (лагерь) | `housing` юнита из `troops.yaml` |
| `garage` | техника и корабли: классы `VEH`, `SEA` (`vehicles:`, `ships:`) | `b_garage` (гараж; корабли — тоже в гараже, верфь только производит) | `housing` юнита |
| `spell` | заклинания (`spells:`) | `b_support_bay` (Центр поддержки) | `housing` заклинания |

Герой housing не занимает: один слот героя, доступность — по `b_command` и усталости (`heroes.md`). ASSUMPTION.
Гарнизон казармы обороны (`b_defense_barracks`) — **отдельная** система обороны и housing лагерей не использует (источник гарнизона — вне объёма DESIGN-3, OQ-RAID0-6).

### 3.2 Вместимость
```
base_cap(pool)  = Σ по построенным (не строящимся с нуля) зданиям пула: capacity_by_level[building.level]
cap(unit)       = floor( base_cap(unit) × (1000 + 10 × army_housing_pct) / 1000 )      # перк §5.5, только пул unit
cap(garage)     = base_cap(garage)
cap(spell)      = base_cap(spell)
```
- `capacity_by_level` — **список целых по уровням здания** в `content/buildings.yaml` (CONTENT-REQ, §11 п.3); без формул с дробями. Здание, которое улучшается, **продолжает работать на текущем уровне** (ASSUMPTION; снимает «принуждающие таймеры»); новая постройка вносит вклад только после завершения строительства.
- Количество зданий — `max_by_hq` из `buildings.yaml` (лагерь: 1/2/3/4 на HQ 1/3/6/8; гараж: 1/2 на HQ 3/7; Центр поддержки: 1/2 на HQ 3/8).
- Ориентир (не решение): `tools/simbattle/assumptions.yaml` — лагерь L1 = 20, макс. уровень = 70 (линейно, 4×70 = 280 «до HQ10», как сказано в `buildings.yaml`/`troops-vehicles-ships.md`); гараж L1 = 20, макс. 70; Центр поддержки 10 housing заклинаний на здание. Для каждого уровня balance записывает явное целое.

### 3.3 Занято
```
used(pool) = Σ stock[u]·housing(u)  +  Σ deployed[*][u]·housing(u)  +  Σ queue.remaining·housing(u)   # u из пула
free(pool) = cap(pool) − used(pool)
```
Т.е. занимают место **и обученные, и стоящие в очередях, и юниты в рейде** (они вернутся, §6.3). Поэтому «обученный юнит влезает всегда» — проверка housing делается один раз, при постановке заказа (§4.3).
Заклинания в очереди и готовые — тоже `used(spell)`; заклинания в рейде — в `deployed`.
Отряд десанта `u_paratrooper` (`group: 4`): housing считается **за каждого юнита** (`housing` в yaml); в Army идёт `Count` юнитов, `Deploy` берёт 4. ASSUMPTION: обучать и отправлять в бой можно только числом, кратным `group` (иначе остаток не сможет высадиться) — `invalid`, `reason: not_multiple_of_group`.

### 3.4 Что нельзя делать с вместимостью
- Нельзя сносить или переносить здание-пул (`b_camp`, `b_garage`, `b_support_bay`), если после этого `used(pool) > cap(pool)`: ответ `conflict`, `reason: housing_in_use` (запрос base, §14). Нельзя сносить производящее здание (`b_barracks`, `b_factory`, `b_shipyard`, `b_support_bay`) с непустой очередью (`reason: queue_not_empty`) и лабораторию с активным исследованием (`reason: research_in_progress`).
- Вместимость не убывает «сама»: уровней-вниз и порчи нет; перки лаборатории не отзываются.

## 4. Обучение: очереди по зданиям

### 4.1 Кто что обучает
| Здание | Обучает | Условие юнита (`unlock` в yaml) |
|---|---|---|
| `b_barracks` | `troops:` (INF, AIR) | `barracks ≥ N` у **этого** здания, `hq ≥ M` |
| `b_factory` | `vehicles:` | `factory ≥ N`, `hq ≥ M` |
| `b_shipyard` | `ships:` | `shipyard ≥ N`, `hq ≥ M`; здание существует только на карте с водой (`requires_water`) |
| `b_support_bay` | `spells:` | `hq ≥ M` (уровень Центра поддержки не требуется) |

### 4.2 Очереди и параллельность
- У **каждого** производящего здания своя очередь (FIFO заказов). Здание обучает **одного юнита за раз**; N зданий — N потоков параллельно (`b_barracks` до 4 на HQ8). «Очередь = 1 здание на 1 тренировку» из `buildings.yaml` — именно это.
- Заказ `{unit_id, count}`: юниты одного заказа обучаются последовательно, каждый — `train_s` (для заклинаний — CONTENT-REQ `train_s`). Готовый юнит **сразу** переходит в `stock` (частичный прогресс виден и не теряется).
- Ленивый пересчёт (целые секунды): голова очереди имеет `unit_started_at`; пока `unit_started_at + train_s ≤ now` → `stock[u] += 1`, `remaining −= 1`, `unit_started_at += train_s` (следующий юнит стартует **в момент** окончания предыдущего, а не «сейчас» — офлайн-прогресс считается точно); пустой заказ снимается, следующий становится головой. В пустую очередь заказ стартует в `now`.
- Лимит длины: `army.queue.max_orders_per_building` (CONTENT-REQ; число решает balance). Превышение — `conflict`, `reason: queue_full`.
- Выбор здания — за игроком (`building_id` в API). UI предлагает «авто»: здание, подходящее по `unlock`, с минимальным оставшимся временем очереди; при равенстве — меньший `uid`.
- Опционально (balance): ключ `train_speed_permille` по уровню здания (`train_s_eff = ceil(train_s × 1000 / speed)`); без ключа скорость от уровня здания не зависит, уровни казармы выше последнего `unlock` (8 из 12) в R1 дают только прочность и вклад в HQ-gate. needs-owner → OQ-ARMY-6.

### 4.3 Постановка заказа (`POST /v1/army/train`)
Проверки в порядке (первая ошибка — результат; ничего не списывается):
1. здание существует, принадлежит игроку, построено (не «с нуля в процессе»), тип подходит юниту (§4.1) — иначе `invalid` / `not_found`;
2. условия `unlock` (уровень **этого** здания, HQ) — `conflict`, `reason: locked`, `details: {need: {barracks: 3, hq: 3}}`;
3. кратность `group` (§3.3) — `invalid`;
4. длина очереди — `queue_full`;
5. **housing:** `need = count × housing(u)`; если `need > free(pool)` → `conflict`, `reason: housing_full`, `details: {pool, capacity, used, free, need, max_count}` (`max_count = floor(free / housing(u))`, для `group`-юнитов — кратно `group`). Заказ **отклоняется целиком** (не усекается): клиент после ответа может повторить с `max_count`; так ответ детерминирован и идемпотентен;
6. стоимость: `cost × count` (fuel для пехоты/дронов/заклинаний; cash и alloy для техники/кораблей — `troops.yaml`) → `Ledger.Apply` с ключом идемпотентности; нехватка — `insufficient_resources` (`details.missing: {fuel: n}`).
Успех: заказ в очереди, ресурсы списаны, ответ — новое состояние армии (§8).
`Idempotency-Key` обязателен (как у мутаций базы): повтор того же ключа не удваивает заказ.
Стоимость юнита **не зависит от его уровня**, а время обучения — от уровня исследований (ASSUMPTION). Calibration расхода fuel — ECON-5 (§11 п.8, OQ-E7).

### 4.4 Отмена и возврат (needs-owner → OQ-ARMY-3)
`POST /v1/army/cancel {order_id, count?}` — `count` по умолчанию = всё `remaining`. Снимаются юниты **с хвоста** заказа; юнит, который обучается прямо сейчас, снимается последним.
Возврат ресурсов (Ledger, ключ идемпотентности):
- ещё не начатые юниты — `army.cancel_refund_unstarted_pct` (рекомендация 100%);
- юнит в процессе — `cancel_refund_pct` из `building_costs.yaml` (50%, как у стройки, base-building.md).
Housing освобождается сразу. Отмена готового (`stock`) юнита невозможна — для этого нет «увольнения» в R1 (ASSUMPTION; освободить место можно только потеряв юнитов в бою).

### 4.5 Ускорение за gems
`POST /v1/army/speedup {building_id}` — мгновенно завершает **всю** очередь здания (все заказы; юниты уходят в `stock`; housing уже зарезервирован, переполнения быть не может).
Цена: `gems = ceil(hours_left^exponent × factor)`, `hours_left = (оставшиеся секунды очереди) / 3600`, параметры `speedup_gems {factor, exponent}` из `building_costs.yaml` (4 и 0.8). Реализация — **та же функция**, что у ускорения построек (`svc/economy`/`svc/base`), не копия формулы. Минимум 1 gem (из-за `ceil`) при непустой очереди; пустая очередь — `invalid`. Нехватка gems — `insufficient_resources`.
Обучение **не** требует билдера (в отличие от стройки).

### 4.6 «Армия не портится»
Нет содержания, износа, срока годности, голода и «дезертирства». Обученный юнит живёт, пока не погибнет в бою. Это явное обещание продукта (`troops-vehicles-ships.md`, `ux-onboarding.md`: «без принуждающих таймеров»). Поэтому очередь можно «зарядить» перед уходом на сутки, а армия ждёт хоть неделю.

## 5. Лаборатория

### 5.1 Правила
- Здание `b_laboratory` (HQ2+, одно; уровней 10). **Одно исследование за раз** на игрока.
- Узел `research.yaml`: `{id, unit|spell|perk, to_level, tier, lab}`. Стоимость и время — по `tiers[tier]` (`fuel`, `hours`), от уровня лаборатории не зависят (ASSUMPTION).
- Условия старта (`POST /v1/lab/research {node_id}`), в порядке:
  1. узел существует, не в `research_done` — иначе `invalid`;
  2. лаборатория построена, `lab.level ≥ node.lab` — `conflict`, `reason: lab_level`, `details: {need: node.lab, have}`;
  3. нет активного исследования — `conflict`, `reason: lab_busy`;
  4. предыдущие узлы того же предмета выполнены (§2.1) — `conflict`, `reason: prerequisite`, `details: {missing: [...]}`;
  5. предмет открыт: `unit.unlock.hq ≤ hq` (для техники/кораблей — также достаточно HQ; наличие здания-производителя не требуется — ASSUMPTION, позволяет исследовать «наперёд»), для заклинаний — `unlock.hq`; для перков условия 5 нет;
  6. `fuel ≥ tier.fuel` — `insufficient_resources`; списание `Ledger.Apply`.
- `research_active = {node_id, started_at, finish_at = started_at + tier.hours·3600, paid}`. Завершение — лениво (§1): в момент `finish_at` узел переходит в `research_done`, лаборатория свободна. Офлайн-прогресс считается по серверному времени.
- Ориентир совместимости с лимитами зданий (из ценника `building_costs`/`structure_bills`: здание-пул растёт на 1 уровень за шаг HQ): лаборатория с `unlock_hq: 2` достигает уровня `L` не раньше HQ `L+1`, т.е. узлы `lab: 1…6` открываются примерно на HQ 2…7 (`r_tank_1`, `r_loot_1`, `r_radar_scan` — `lab: 6` → ~HQ7; `r_tank_1` вдобавок требует `v_tank` `unlock.hq: 7`). Это следствие правил базы, отдельной проверки в лаборатории нет.

### 5.2 Отмена
`POST /v1/lab/cancel`: возврат `cancel_refund_pct` (50%) от `paid`; узел не выполнен; лаборатория свободна. needs-owner: OQ-ARMY-3 (общая политика возвратов).

### 5.3 Ускорение за gems
`POST /v1/lab/speedup`: завершает исследование сейчас; цена — та же функция `ceil(hours_left^0.8 × 4)` (§4.5). Уровень срабатывает как при обычном завершении (§2.2).

### 5.4 Лаборатория и стройка
Улучшение лаборатории не останавливает исследование (ASSUMPTION, как §3.2). Снос лаборатории с активным исследованием запрещён (§3.4).

### 5.5 Перки (`perk` в узле)
Формат сейчас — строка `"key+N"`; CONTENT-REQ: структурное `perk: {key, value}` (§11 п.5). Перки складываются по ключу (каждый узел действует один раз):
| key | Эффект | Потребитель |
|---|---|---|
| `army_housing_pct` | `+value%` к `base_cap(unit)` (формула §3.2, округление вниз один раз по сумме). На гараж и Центр поддержки **не** действует (ASSUMPTION; имя «army» — про лагеря) | ARMY (housing) |
| `raid_loot_pct` | множитель добычи: `loot = min(victim_lootable × 0.225 × star_mult × (100 + Σvalue)/100, attacker_cap)`; `attacker_cap` (`raids.loot_cap_pct_of_attacker_storage`) перком **не** увеличивается («capped; respects raids.loot_cap», `note` в yaml) | raid/economy |
| `scan_reveals_traps` | булев: при предпросмотре цели сервер добавляет в клиентский Snapshot скрытые мины/пружины как `Revealed` (см. `battle-sim.md` §8.4, OQ-7.8). Связь с `b_radar` — needs-owner → OQ-ARMY-5 | raid |
Модуль ARMY только публикует `perks` (`GET /v1/army`), применяют их потребители.

## 6. Формирование Army для боя и потери

### 6.1 Вход (`POST /v1/raids/start` и `campaign/{stage}/start`)
Тело клиента (контракт `docs/03-api.md`): `army: [{id, count}]`, `spells: [{id, count}]`, `hero: {id}|null`. **Клиент уровень не присылает.** Сервер проверяет и строит `sim.Snapshot.Army`.
Проверки (первая ошибка — `invalid`/`conflict`, `details.reason`):
1. `count ≤ stock[id]` (для заклинаний — `spells[id]`) → `no_stock`;
2. `count` кратен `group` для десанта → `not_multiple_of_group`;
3. суммарный housing выбранных ≤ `cap(pool)` каждого пула (по построению всегда верно; проверка защищает от подделки) → `housing_exceeded`;
4. корабли (`SEA`) допустимы, только если карта цели содержит воду (`maps.<id>.water`) → `ship_no_water` (ASSUMPTION; UI скрывает корабли для сухих целей);
5. герой: выбран, не ранен, доступен по `b_command` (`heroes.md`) → `hero_unavailable`;
6. не более одного активного рейда игрока (если иначе — правило raid-модуля).
Пустой выбор допустим только для пропуска (бой без юнитов `Start` не пройдёт — `battle-sim.md` §4.1).

### 6.2 Escrow и уровни в тикете
После успешных проверок, **в одной транзакции** с созданием `RaidTicket`:
- выбранные юниты и заклинания **вычитаются** из `stock`/`spells` и записываются как `deployed[raid_id]` (`used` не меняется);
- слот `sim.Army` собирается: `Slot{ID: id, Level: Level(id), Count: count}` по состоянию `research_done` **на момент `start`**; уровень зафиксирован в тикете и в реплее (вместе с `content_version`);
- `Spells`/`Hero` — аналогично (`Level(c_*)`, уровень героя из системы героев).
Сервер, пересчитывая бой по журналу (`raids/finish`), берёт `Army` из тикета, а не из клиента.

### 6.3 Итог и потери
По `raids/finish` (или по истечении тикета, §6.4) сервер берёт из `sim.Result`:
```
UnitsLost[(ID, Level, Count)]   SpellsUsed[(ID, Level, Count)]   HeroDamageTaken   HeroSurvived
```
и в той же транзакции:
- `stock[u] += deployed[u] − lost[u]` (выжившие возвращаются в запас; у `u_breacher` подрыв = потеря; погибшие в транспорте — потеря);
- потерянные юниты исчезают навсегда (ресьюма у медика нет — `troops-vehicles-ships.md`);
- `spells[s] += deployed[s] − used[s]` (неиспользованные заклинания **возвращаются**);
- housing пересчитывается автоматически (`used` уменьшился на потери);
- герой не теряется; `HeroDamageTaken` → таймер отдыха (`heroes.md`, ≤ 8 ч);
- `retreat` и истечение `battle.time_limit_s` потерь не добавляют сверх фактических гибелей: отступившие юниты на поле возвращаются живыми.
Резолв идемпотентен по `raid_id` (повторный `finish` не возвращает юнитов дважды).
В кампании армия *тратится* так же (`campaign.md`).

### 6.4 Тикет без `finish` (needs-owner → OQ-ARMY-7)
Если `finish` не пришёл к `expires_at` (+ grace, ключ raid): сервер закрывает рейд как `retreat` на ходу 0 — `deployed` возвращается в запас целиком, рейд засчитывается как поражение по правилам raid-модуля (кубки `loss_base`, стоимость поиска не возвращается). Рекомендация: так, а не «все юниты потеряны» (нет «потеряй всё»).

### 6.5 UI «Экран выбора армии» (`raids-pvp.md` UX)
Пресеты: «Вся армия» (всё из запаса, кроме явно снятого), «Рекомендация против этой базы» (подсказка по `fav` и составу обороны — клиентская эвристика, не гарантия), «Прошлый состав». Счётчик housing по пулам, уровни юнитов, предупреждение «корабли не применимы» (§6.1 п.4), блок «потеряете ~X» не показываем (нет прогноза потерь — ASSUMPTION).

## 7. Стартовая армия новичка и онбординг

Цель (`economy.md`, критерий 2): в первую сессию игрок имеет первую армию и проходит шаги 1–6 `ux-onboarding.md` (≥70%).
1. **Лагерь уже стоит.** ASSUMPTION: `content/start_layout.yaml` (OQ-S6) содержит `b_camp` L1 (готовый, без таймера) вместе с HQ — без лагеря `cap(unit) = 0` и обучение невозможно. Казарма строится по сценарию туториала (шаг 3).
2. **Туториальное «мгновенно».** Шаги 3–4 ux («казарма мгновенно», «5 стрелков мгновенно») реализуются **единым флагом сервера** `tutorial_instant` (OQ-E6): первая казарма, первая постановка заказа и первое улучшение штаба завершаются бесплатным ускорением. Для армии это: **первый** заказ игрока (`unit_id`/`count` любые) в первой казарме завершается сразу, при условии прохождения `army.tutorial.free_finish_first_order`. Остальные заказы — по обычным правилам, без льгот.
3. **Стартовая армия** = `start_army` (CONTENT-REQ): 5 × `u_rifleman` (число из ux-onboarding шаг 4; fuel 5×25=125 ≤ `start_grant.fuel` 600). Игрок обучает её сам (шаг 4) — это учит очереди и housing; если он пропустил шаг, армия **не** выдаётся автоматически (ASSUMPTION; запас fuel есть, кнопка «Обучить» подсвечена).
4. **Первый бой** — кампания этап 1 (шаг 5): `Army` = эти 5 стрелков, уровень 1 (узлов нет). Потери — по §6.3; если стрелки погибли, повторное обучение стоит fuel (грант + сборщики покрывают, `economy.md`).
5. **Лаборатория** открывается на HQ2: в туториале — подсказка «Улучшите стрелка» после HQ2 (`r_rifle_1`, tier 1, 800 fuel, 2 ч): первое исследование **не** ускоряется бесплатно (льгота только на первый заказ армии).
6. **Первый PvP-рейд** (шаг 8) на «тренировочной» базе: пресет «Вся армия» выбран по умолчанию.
Метрики: время до первого обучения юнита ≤ 3 мин сессии; доля, использовавшая экран выбора армии без отказов сервера, ≥ 95%.

## 9. Примеры (фикстуры, не баланс)

> Фикстура F-ARMY-1: HQ3, 2 лагеря L1 (по 20 housing, как «ориентир» §3.2 — **тестовое число**), 2 казармы L2 (A и B), `u_rifleman` housing 1 / 12 с / 25 fuel, `u_sniper` housing 2, `u_brawler` housing 4 / 45 с / 110 fuel (`unlock: barracks 2, hq 2`). Кошелёк: fuel 2000.

### 9.1 Обучение с переполнением лагеря
Исходно: `stock` = 12 стрелков + 2 снайпера → 12 + 4 = 16; в казарме A идёт заказ 3 × штурмовик (3×4 = 12). `cap(unit) = 40`, `used = 28`, `free = 12`.
| Шаг | Действие | Результат |
|---|---|---|
| 1 | заказ B: 4 штурмовика (`need` 16) | `conflict housing_full`, `{capacity 40, used 28, free 12, need 16, max_count 3}`; fuel не списан |
| 2 | заказ B: 3 штурмовика (`need` 12) | ок; fuel −330; `used 40`, `free 0`; B стартует параллельно A: обе очереди заканчиваются через 135 с (3×45) |
| 3 | заказ A: 1 стрелок | `housing_full`, `free 0`, `max_count 0` |
| 4 | исследование `r_camp_cap` завершено (`army_housing_pct+5`) | `cap = floor(40 × 1050/1000) = 42`, `free 2` |
| 5 | заказ A: 2 стрелка | ок (fuel −50); встают в хвост A: завершение A на 135 + 24 = 159 с |
| 6 | ускорение очереди A (`hours_left = 159/3600 ≈ 0,044`) | `ceil(0,044^0,8 × 4) = 1` gem; все юниты A сразу в `stock`, housing не меняется |
| 7 | отмена заказа B в момент t = 50 с (1 юнит готов, 1 в процессе, 1 нет) | юнит готов — остаётся; в процессе: 50% от 110 = 55 fuel; не начат: 100% (рекомендация) = 110 fuel; `used` −8 |

### 9.2 Исследование с апгрейдом уровня
Фикстура: HQ4, лаборатория L3, 20 `u_rifleman` L1, fuel 4000. Формулы `battle-sim.md` §3.2, `battle.turn_s = 2` (T10 = 20), `level_growth` войск 1180/1160.
| t | Событие | Эффект |
|---|---|---|
| 0:00 | `POST /v1/lab/research {r_rifle_1}` (tier 1: 800 fuel, 2 ч, `lab 1`) | fuel 3200; `research_active.finish_at = 2:00` |
| 0:30 | `r_rifle_2` | `conflict lab_busy` (одно за раз) |
| 1:59 | игрок стартует рейд | слот `{u_rifleman, Level 1, Count 20}`: `max_hp 55`, `dmg = floor(90·1000·20/100000) = 18` |
| 2:00 | узел выполнен | `Level(u_rifleman) = 2` для всех 20 (и обучаемых); бой из 1:59 остаётся на L1 |
| 2:01 | новый рейд | слот L2: `Mhp[2] = 1180` → `max_hp = floor(55·1180/1000) = 64`; `Mdps[2] = 1160` → `dmg = floor(90·1160·20/100000) = 20` |

| — | отмена `r_rifle_2` до завершения | возврат 50% от 3000 = 1500 fuel; уровень остаётся 2 |

### 9.3 Формирование Army, бой, потери
Запас: 40 × `u_rifleman` (L4), 6 × `u_brawler` (L2, `r_brawler_1` выполнен), 2 × `u_medic` (L1, узла нет), 2 × `v_humvee` (L1), 2 × `c_airstrike` (L1, housing 2). Пулы: `unit` 40·1 + 6·4 + 2·3 = 70; `garage` 2·5 = 10; `spell` 2·2 = 4.
Клиент: `POST /v1/raids/start {target_id, army: [{u_rifleman,30},{u_brawler,6},{u_medic,2},{v_humvee,2}], spells: [{c_airstrike,2}], hero: {h_commander}}`.
Сервер → `sim.Snapshot.Army` (уровни сервер подставляет сам): `[{ID u_rifleman, Level 4, Count 30}, {u_brawler, 2, 6}, {u_medic, 1, 2}, {v_humvee, 1, 2}]`, `Spells [{c_airstrike, 1, 2}]`, `Hero {h_commander, Level из heroes}`. `stock` → 10 стрелков; `deployed` записан.
Результат боя: `UnitsLost [{u_rifleman,4,11},{u_brawler,2,2},{v_humvee,1,1}]`, `SpellsUsed [{c_airstrike,1,2}]`, `HeroDamageTaken 340`, `HeroSurvived true`.
Расчёт: стрелки `10 + (30−11) = 29`; штурмовики `0 + (6−2) = 4`; медики 2; Хамви 1; аирстрайков `0 + (2−2) = 0`. `used(unit) = 29 + 16 + 6 = 51` (свободно 19 = 11 + 2·4), `used(garage) = 5`, `used(spell) = 0`. Герой: таймер отдыха по `HeroDamageTaken` (`heroes.md`).

## 10. User stories и Acceptance

**US-A1 Армия и места.** Как игрок я вижу запас, уровни юнитов и занятость лагерей/гаража/Центра поддержки.
*AC:* три пула показывают `used/capacity` с учётом очередей и юнитов в рейде; перк `army_housing_pct` отражён в `capacity` пула `unit` и подписан; уровень типа показан бейджем.

**US-A2 Обучение.** Я ставлю в очередь юнитов выбранного здания и получаю их по таймеру, в том числе офлайн.
*AC:* юнит доступен, только если уровень этого здания и HQ ≥ `unlock`; fuel/cash/alloy списаны при постановке; готовые юниты попадают в запас сами; два здания обучают параллельно; повторный запрос с тем же `Idempotency-Key` не создаёт второй заказ.

**US-A3 Защита от переполнения.** Я не могу заказать больше, чем помещается.
*AC:* заказ, превышающий `free`, отклоняется целиком с `housing_full` и `max_count`; ресурсы не списываются; после отмены/потери юнитов/апгрейда лагеря место освобождается; нельзя снести лагерь, если `used > cap` после сноса.

**US-A4 Очередь и отмена.** Я вижу очередь по зданиям и могу отменить заказ.
*AC:* отмена возвращает 100% (не начатые, рекомендация) и 50% (в процессе); частичный прогресс (готовые юниты) сохраняется; housing освобождается сразу.

**US-A5 Ускорение.** Я могу за gems завершить очередь здания.
*AC:* цена = `ceil(hours_left^0.8 × 4)` из `building_costs.yaml` (общая функция), ≥ 1 gem; после ускорения все юниты в `stock`; переполнения нет.

**US-A6 Исследование.** Я запускаю улучшение, ограниченное уровнем лаборатории.
*AC:* одно за раз (`lab_busy`); `lab_level` проверяется; fuel списан; таймер серверный; ускорение и отмена работают; завершение офлайн применяется при следующем чтении.

**US-A7 Уровень юнита.** После исследования все юниты этого типа сильнее.
*AC:* `Level(item) = max to_level` по выполненным узлам, 1 без узлов; уровень получают все экземпляры (обученные ранее и в очереди); уже выданный `RaidTicket` не меняется; клиент уровень не присылает.

**US-A8 Перки.** Перки лаборатории влияют на вместимость, добычу и разведку.
*AC:* `army_housing_pct` поднимает `cap(unit)` и не трогает гараж/Центр; `raid_loot_pct` не превышает кап добычи; `scan_reveals_traps` выставляет `Revealed` у скрытых ловушек в предпросмотре.

**US-A9 Состав боя.** Я выбираю состав из запаса перед боем.
*AC:* нельзя отправить больше, чем в запасе; десант — кратно `group`; корабли — только если у цели есть вода; выбранные юниты исчезают из запаса на время боя, но продолжают занимать housing.

**US-A10 Потери и возврат.** После боя я вижу, кого потерял и кто вернулся.
*AC:* `stock += deployed − UnitsLost`; неиспользованные заклинания возвращаются; повторный `finish` не дублирует возврат; отступление не наказывает сверх фактических гибелей; герой не теряется.

**US-A11 Новичок.** Новичок проходит путь «казарма → 5 стрелков → бой» за первые минуты.
*AC:* лагерь есть с начала; первый заказ завершается бесплатным ускорением один раз; `start_army` не выдаётся автоматически; первый бой кампании использует эти 5 юнитов.

**US-A12 Армия не портится.** Армия остаётся без содержания.
*AC:* ни один таймер/ресурс не уменьшает запас юнитов вне боя; тест: `stock` через 30 суток офлайна равен исходному.

## 12. Допущения (ASSUMPTION), собранные вместе
1. Уровень — свойство типа; в таблице `army` колонка `level` не нужна (§1).
2. Стоимость и время обучения не зависят от уровня исследований; цена исследования и время — по tier, не зависят от уровня лаборатории (§4.3, §5.1).
3. Здание продолжает работать во время улучшения; новое — после постройки (§3.2, §5.4).
4. `used` включает юнитов в очередях и в рейде (§3.3).
5. Заказ при нехватке места отклоняется целиком (§4.3).
6. Нельзя «уволить» готового юнита; единственный способ освободить место — потеря в бою или отмена заказа (§4.4).
7. Перк `army_housing_pct` — только лагеря; перки складываются; `raid_loot_pct` не повышает кап (§5.5).
8. Исследование предмета не требует построенного производящего здания, только открытого HQ (§5.1).
9. Герой не занимает housing; гарнизон обороны — отдельная система (§3.1).
10. Корабли в рейде — только против карты с водой (§6.1).
11. Лагерь есть в стартовой раскладке; `start_army` не выдаётся автоматически (§7).
12. Кратность `group` для десанта при обучении и отправке (§3.3).
13. Без прогноза потерь в UI (§6.5).
